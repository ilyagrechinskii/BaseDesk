# Постоянные ветки команды

У каждого участника одна постоянная именная ветка. Новые feature-ветки для отдельных Issues не используются.

| Участник | Ветка | Ответственность |
| --- | --- | --- |
| Илья | `ilya` | Архитектура, организация, интеграция |
| Александр | `alexander` | Electron, интеграция экранов |
| Андрей | `andrey` | API, EF Core, PostgreSQL |
| Наталья | `natalia` | Общие компоненты и CSS |
| Никита | `nikita` | Главная страница |
| Дмитрий | `dmitry` | Клиенты |
| Артём | `artem` | Задачи |

Ветка создаётся от актуальной `origin/main` один раз. Если именная ветка уже существует локально или удалённо, её продолжают без пересоздания и сброса. Рабочие изменения делаются только в своей ветке. `main` принимает изменения через PR после проверки, `legacy/electron-net` остаётся архивом. Не изменять файлы соседнего участника без согласования владельца.

## Первый запуск своей ветки

Команды ниже выполняет сам участник. `git status` должен показывать чистое рабочее дерево, включая индекс. Если есть локальные изменения, сначала завершите их в своей ветке или согласуйте безопасное сохранение; не применяйте reset/clean и не переносите их поверх чужих файлов.

```powershell
git status
git fetch origin
git branch -avv
```

Далее выбрать ровно один сценарий (пример для Никиты):

- Нет `nikita` ни локально, ни на GitHub: `git switch -c nikita origin/main`.
- Ветка есть только на GitHub: `git switch --track origin/nikita`.
- Ветка есть локально: `git switch nikita`.

Если ветка уже опубликована, сначала включите её актуальные удалённые изменения командой `git merge --ff-only origin/nikita`. Если fast-forward невозможен, остановитесь и вместе с Ильёй разберите расхождение; не перезаписывайте удалённую историю. Затем синхронизируйтесь с `origin/main` по порядку ниже.

## Работа над задачей

Одна задача — один PR из своей постоянной ветки в `main`. Включайте только завершённые изменения этой задачи. Не начинайте следующую задачу в той же ветке до объединения текущего PR и синхронизации: иначе новые коммиты автоматически попадут в открытый PR.

Каждый коммит — одно понятное изменение, которое можно проверить отдельно. Автор самостоятельно выполняет индексацию, коммит и push со своими Git-данными. Не менять чужое авторство и не добавлять соавторов автоматически. Имена коммитов: `docs: ...`, `chore: ...`, `feat: ...`, `fix: ...` по смыслу изменения.

Перед PR проверьте `git diff origin/main...HEAD`: там должны быть только изменения текущей задачи. Ссылки на Issue, проверка и правила объединения описаны в [pull-request-review.md](pull-request-review.md).

## Синхронизация после объединения PR

Постоянные ветки не удаляются после PR. Предпочтительно объединять PR с сохранением коммитов (merge commit), чтобы небольшие логические коммиты оставались в истории. Squash или переписывание истории требуют отдельного решения команды и не используются по умолчанию.

На чистом рабочем дереве в своей ветке (пример для Никиты):

```powershell
git status
git fetch origin
git switch nikita
git merge --ff-only origin/nikita
git merge origin/main
git diff origin/main...HEAD
git status
git push origin nikita
```

После первого PR `origin/nikita` уже должна существовать. Если ветка ещё не публиковалась, шаг с `origin/nikita` пропускают и при первой публикации используют `git push -u origin nikita`.

После полного включения завершённой задачи в `main` разница с `main` должна быть пустой перед началом следующей задачи. Если она не пустая — сначала разберите оставшиеся коммиты. Merge из `origin/main` в свою ветку сохраняет историю и не меняет `main`. Rebase опубликованных постоянных веток и force-push не применяются.

При конфликтах merge не выбирайте массово «всё моё» или «всё чужое». Просмотрите каждый конфликт и согласуйте затронутые файлы с владельцем. После исправления автор сам индексирует разрешённые файлы, завершает merge и проверяет результат. Если решение пока неизвестно, `git merge --abort` возвращает состояние до merge; поэтому слияние начинают только с чистого дерева. Ошибки доступа и расхождение удалённой ветки не исправляют принудительным push.
